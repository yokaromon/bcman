# Require managed ykr for final OCR and Contact structuring

User orientation, OCR and Contact corrections remain feedback candidates until an authorized reviewer verifies them against the source Business Card and explicitly accepts them into a training set; runtime corrections never become labels automatically.

Additional training starts only after a pinned pretrained baseline and failure analysis demonstrate that it addresses an unmet acceptance gate. It may use development data and approved feedback candidates but never the fixed holdout for training, prompt or threshold tuning, or model selection; every trained artifact forms a new Recognition Release.

Final OCR and Contact structuring in both pickup and production require the user-managed `app.ykr.ltd` service. Card Extraction and Reading Orientation remain local, bundle their model versions, checksums and applicable license notices, forbid runtime model downloads and can finish without network access. Local PaddleOCR text detection supplies polygonal text regions and reading-order candidates; the managed ykr OCR response supplies ordered transcription lines, printed-or-handwritten source and legibility, but never guesses pixel coordinates. Their persisted alignment retains both forms of evidence. A managed-only line keeps a null region, a local-only region keeps null text, and each is marked unmatched rather than being forced together or discarded. Managed-only text remains eligible for Contact structuring, but a field supported only by unmatched text is review-flagged. Contact structuring receives only the validated OCR line identifiers, text, reading order, local geometry, source and legibility; it does not receive the card image again and cannot introduce unsupported text into an accepted field. Structured fields use exactly three semantic states: present requires a non-null source-preserving `display_value` and source lines, absent requires a null display value and no sources, and unreadable requires a null display value plus source lines while keeping any tentative text only as `candidate_value` and always setting a Review Flag. Multi-line values retain every contributing line identifier. Local deterministic normalization derives `normalized_value` for validation, search and evaluation without letting managed AI rewrite or replace the displayed value. A format-validation failure preserves the display value and evidence and adds a Review Flag instead of consuming an API retry. If a cited value is not derivable from its managed OCR lines, it is retained only with `evidence_status: unsupported`, review-flagged, blocked from registration until user edit or explicit acceptance, and counted as a hallucination in evaluation rather than retried. Violating the JSON structure, semantic state or evidence-identifier invariants does consume that stage's retry budget. PP-OCRv5 recognition text may still support local orientation and a separately stored development diagnostic, but it neither replaces nor silently merges with managed transcription. Managed OCR and Contact structuring remain separate stages with independently stored results. A transport error, timeout or structurally invalid response—including a JSON Schema violation, missing required key or invalid value type—consumes that stage's retry budget. Each stage permits its initial request plus one automatic retry, for at most four managed requests per card; successful OCR is reused when only structuring fails. Normal resume also reuses any successful result whose fingerprint matches the oriented-image hash, orientation, local detector model, ykr model, prompt and schema versions. Explicit user re-recognition bypasses that reuse, adds a new result and never overwrites earlier results or edited values. Every local and managed model, prompt, schema, normalization rule and threshold is pinned as one immutable Recognition Release; floating aliases and automatic updates are forbidden, and any change or fine-tuning must pass development regression and the full fixed-holdout acceptance gates as a new candidate. Ordinary ykr request and error logs exclude images, request bodies, OCR text and Contact values, retaining only request identity, timing, pinned model, HTTP status and duration; only separately selected and human-authorized data may enter training. A second stage failure marks only that Business Card Retry Required while peers continue, without automatic local fallback or an unbounded loop. Production promotion evaluates the managed output against OCR, Contact Field and Recognition Pipeline Acceptance on the fixed unseen holdout.
